# 01. ビジョンと設計原則

ステータス: **提案（レビュー待ち）**

## mcrl とは

Mackerel の API を端末から扱うための CLI。読み方は「マクレル」。

対象とする利用者と場面:

| 利用者 | 場面 |
|---|---|
| SRE・運用担当（人間） | 障害対応中のアラート確認、ホストの退役、ダウンタイム設定、ログ・トレースの調査 |
| スクリプト・CI | デプロイ時のアノテーション、cron からのチェック監視レポート、メトリクス投稿 |
| 監視設定を管理するチーム | 監視・ダッシュボード設定のエクスポート・差分・適用 |
| AI エージェント | LLM エージェントが CLI 経由で Mackerel を調べる・操作する |

## 設計原則

### 1. 出力は JSON だけ

- 出力は API のレスポンスに沿った JSON（と JSONL）だけにする。表などの人間向け形式は持たない
- 人間が読むときは TTY でのインデント・色付けと、内蔵の `--jq` で絞り込む
- JSON 出力・終了コード・エラー形式は **互換性を保証する公開インターフェース** として扱う

### 2. 一貫した文法

- `mcrl <リソース> <動詞> [引数] [フラグ]` に統一する（例: `mcrl host list`、`mcrl alert close`）
- 同じ意味のフラグはどのコマンドでも同じ名前・同じ挙動（`--service`、`--since`、`-o`）
- API のパスや命名の不揃い（[api-notes.md](api-notes.md)）は CLI 側で吸収し、利用者には見せない

### 3. 安全が既定

- 破壊的操作は TTY では確認を求め、非 TTY では `--yes` がなければ実行しない
- 全ての更新系コマンドに `--dry-run`（送信予定のリクエストを表示して終了）
- Read-Modify-Write では未知のフィールドを絶対に落とさない（監視設定の PUT で `isMute` が消える類の事故を構造的に防ぐ）

### 4. API の 100% を覆い、それ以上を足す

- 全エンドポイントを型付きコマンドで覆う。追いつかない部分は `mcrl api` で生 API を叩ける
- そのうえで、API 単体では面倒な操作をコマンド化する
  - コマンドを実行して結果をチェック監視として報告する（`mcrl check run`）
  - コマンドの前後をグラフアノテーションで囲む（`mcrl annotation wrap`）
  - ログの追従（`mcrl log tail`）
  - `$EDITOR` での設定編集と差分確認（`mcrl monitor edit`）

### 5. 速く、軽く、どこでも動く

- 単一バイナリ、ランタイム依存なし、起動 50ms 以内を目標
- macOS / Linux / Windows、amd64 / arm64
- 監視対象ホスト上でも気軽に置ける（mackerel-agent の隣で cron から使える）

### 6. 隠さず、驚かせない

- `--debug` で HTTP リクエスト・レスポンスを全て見せる（API キーは伏せる）
- 自動リトライ・自動ページング・名前解決など CLI が裏でやることは、`--debug` で必ず追える
- 暗黙の設定ファイル読み込みはしない（読む場所は `mcrl config path` で一覧できる）

## 非目標

- **既存ツールとの互換性**: コマンド名・フラグ・出力形式を既存ツールに合わせることはしない
- **mackerel-agent の代替**: メトリクス収集エージェントは作らない（投稿 API を叩く道具は提供する）
- **Terraform の代替**: 宣言的管理は「手元の設定をサッと同期する」軽量な範囲に留める（[07-declarative.md](07-declarative.md)）
- **Web コンソールの再現**: 表・グラフ・TUI などの見た目は作らない。見たいときは `mcrl open` で Web コンソールを開く

## 成功の基準

- 障害対応中に Web コンソールを開かずにアラート確認〜クローズまで完結できる
- `mcrl <リソース> --help` を見れば迷わず使える（ドキュメントを読まずに済む）
- シェルスクリプトから使うとき `jq` を別途インストールしなくてよい（`--jq` 内蔵）
- AI エージェントが `--help` と JSON 出力だけで正しく操作できる
